Ein Herz,
mehrere Adressen.

HAI ist der Kern. Verkauf, Einstieg und Werkzeuge liegen auf eigenen Domains. Zwei davon sind live; die übrigen sind geplant. Diese Seite trennt beides.

Die Adressen ansehen Was heute live ist
Live · 1 von 8

Keine Roadmap mit Terminen. Eine Bestandsaufnahme mit Datum: was live ist, was Absicht ist und was noch fehlt.

01 / Adressen

Bestand

Acht Adressen, eine Ordnung.

Jede Domain bekommt genau eine Aufgabe. Die Tabelle nennt Domain, Rolle, Status und Verantwortung. „Live“ heißt: als eigene Domain ausgeliefert — auf diesem Worker oder einem eigenen. „Geplant“ heißt: vorgesehen, aber heute ohne Route.

human-agent-interface.com Herz: erklärt HAI. live Definition, Belege, Sprache.
agentfähig.de Verkauf: Setup, Werkstatt, Teams. live · eigener Worker Angebot und Abschluss.

Gezählt: acht Domains, zwei live: diese Seite und agentfähig.de (eigener Worker). Die zehn Test-Worker des Fleets laufen unter workers.dev und haben keine Domain-Route (Stand 08.10.2026).1

Rechtlich: Impressum und Datenschutz nennen fünf dieser acht Domains. Es fehlen agentcontrol.systems, agent-human-interface.com und humanagnet.com.2

02 / Die Regel

Zuständigkeit

Eine Domain, eine Aufgabe.

Das Herz erklärt. Der Verkauf verkauft. Die Werkzeuge beweisen. Keine Domain wiederholt eine andere — sonst konkurrieren zwei Seiten um dieselbe Suche und dieselbe Aussage.

Die kanonische Adresse zeigt immer auf die Domain, die den Inhalt besitzt. Nicht auf die, über die jemand zufällig hereinkommt.

Das ist keine SEO-Übung. Es ist dieselbe Regel wie im Betrieb: eine Aufgabe, ein Besitzer, eine Quelle.

Prüfstein: Lässt sich die Aufgabe in einem Satz nennen? Wenn nicht, gehören zwei Dinge auf zwei Domains.

03 / Live

Bestand

Zwei Adressen sind live.

www.human-agent-interface.com liefert diese Seiten aus. Sie ist das Herz und die kanonische Quelle.

agentfähig.de ist live auf einem eigenen Host und liefert eine eigene Verkaufsseite aus. Es ist nicht an diesen Worker gebunden; im Worker gibt es für agentfähig.de keine Route.

Würde die Domain auf denselben Worker zeigen, lieferte die Assets-Schicht die Startseite aus — mit dem Canonical des Herzens. Zwei Hosts, ein Inhalt, und die Verkaufsdomain würde sich als Herz ausgeben. Deshalb bleibt agentfähig.de auf einem eigenen Worker.

Die Verkaufsseite unter /agentfaehig/ bleibt als interne Fassung erreichbar. Ihr Canonical muss auf die besitzende Domain zeigen, sobald die eigene Domain der kanonische Ort ist.

agentfähig.de bleibt auf seinem eigenen Worker. Eine Bindung an dieses Mesh ist eine Entscheidung, kein Defekt.

Geprüft am 30.10.2026: agentfähig.de liefert HTTP 200 auf einem eigenen Host („agentfähig.de — Was willst du heute erledigen lassen?“). Die Domain ist nicht an diesen Worker gebunden; die Verkaufsseite unter /agentfaehig/ ist ebenfalls live. Offen: Canonical der eigenen Verkaufsdomain.

04 / Nächste Schritte

Reihenfolge

Vier Schritte, einzeln geprüft.

Kein Schritt beginnt, bevor der vorige überprüfbar ist.

  1. 01

    agentfähig.de kanonisieren und Entscheidung dokumentieren.

    Eigener Worker bleibt; Canonical auf die eigene Verkaufsdomain prüfen. Keine Bindung an dieses Mesh ohne Entscheidung.

  2. 02

    Den Verkauf getrennt ausliefern.

    Eigener Deploy für die Verkaufsseite. Das Herz wird nicht zusammen mit dem Verkauf ausgerollt.

  3. 03

    Die übrigen Domains einzeln binden.

    Eine Domain pro Schritt, jede mit eigener Route, eigenem Canonical und eigenem Inhalt. Kein Bündel.

  4. 04

    Eine Quelle für den Deploy behalten.

    Nur 03_HAI. Vor jedem Deploy Commit und Datum prüfen.

Abbruchkriterium: Zwei Domains mit demselben Inhalt sind kein Fortschritt, sondern ein Rückschritt.

05 / Checkouts

Betriebsrisiko

Drei Checkouts, ein Risiko.

Dasselbe Repository liegt an drei Orten. Nur einer ist der Deploy-Stand.

Ein Deploy aus dem falschen Ordner veröffentlicht einen alten Stand — ohne Fehlermeldung, ohne Warnung. Die Seite sieht intakt aus und ist trotzdem falsch.
