# /auto — Smart Auto-Delegation

Analysiere den Task und wähle automatisch die optimale Methode. NIE beim User fragen.

**Task:** $ARGUMENTS

## Routing-Logik (in Reihenfolge prüfen)

1. Task ist eine Frage ("?" am Ende, "was ist", "wie funktioniert", "explain", "what is") → direkt antworten, KEIN Delegate
1b. Task ist lint/format/test-run/deps/git-overview/find/health (kein LLM noetig) → CLI: `bash ~/.claude/cli/<script>.sh` — $0, sofort
2. Task enthält "test" + Analyse/Fix noetig → /test Pattern: `mcp__opencode__opencode_run` mit test-fokussiertem Prompt
3. Task enthält "research", "suche", "best practice", "what's the best", "compare" → /research Pattern: `mcp__gemini__ask-gemini`
4. Task enthält "refactor", "multi-file", "rename everywhere", "umbenennen überall", "3+ files" → /crew Pattern: Skill `crew`
5. Task ist kleiner Fix (1-2 Dateien, klar umgrenzt, kein Context nötig) → /chef-lite Pattern: `mcp__opencode__opencode_ask` direkt
6. Alles andere → /chef Pattern: `gather-context-enhanced.sh` + `mcp__opencode__opencode_run`

## Ausführung

Führe die gewählte Methode sofort aus — kein weiteres Nachfragen.

**OpenCode Fallback:** Bevor du chef/chef-lite/test Pattern nutzt, prüfe ob OpenCode MCP verfügbar ist (ToolSearch "opencode"). Falls NICHT verfügbar → führe den Task direkt aus (Claude Code eigene Tools: Read, Edit, Write, Bash). Kein Warten, kein Fehler — einfach selbst machen.

Für chef Pattern:
1. Run `bash ~/.claude/hooks/gather-context-enhanced.sh "$(pwd)" "$ARGUMENTS"` → CONTEXT
2. Call `mcp__opencode__opencode_run` mit CONTEXT + Task, `directory`: pwd, `providerID`: "minimax-coding-plan", `modelID`: "MiniMax-M2.5", `maxDurationSeconds`: 300
3. **Fallback:** Falls MCP timeout (>60s) oder Fehler → Task direkt mit Claude Code Tools erledigen

Für chef-lite Pattern:
1. Call `mcp__opencode__opencode_ask` mit Task direkt, `directory`: pwd, `providerID`: "minimax-coding-plan", `modelID`: "MiniMax-M2.5"
2. **Fallback:** Falls MCP nicht erreichbar → Task direkt erledigen

Frage Samuel:

> (Ein Satz. Kein "und". Kein "ausserdem". EIN Ding.)

## Schritt 2: Ziel bestaetigen

Wiederhole das Ziel in deinen Worten und frage:

> **Session-Ziel: [Ziel]. Stimmt das?**

## Schritt 3: Bei JEDER neuen Anfrage pruefen

Bevor du eine neue Anfrage ausfuehrst, pruefe:

**Passt diese Anfrage zum Session-Ziel?**

- **JA** → Ausfuehren, kurzer Hinweis: "Passt zum Ziel ✓"
- **NEIN** → Freundlich bremsen:

> **Gute Idee! Aber das ist nicht unser Ziel fuer heute.**
> Optionen:
> 1. **Parken** — Ich notiere es fuer spaeter (in SESSION_LOG.md unter "Geparkte Ideen")
> 2. **Bewusst wechseln** — Wir aendern das Session-Ziel zu diesem neuen Thema
> 3. **Kurzer Abstecher** — Max 5 Minuten, dann zurueck zum Ziel

## Schritt 4: Regelmaessige Check-ins

Nach jedem groesseren Arbeitsschritt:

> **Focus-Check: Wir arbeiten an [Ziel]. Fortschritt: [kurze Einschaetzung]. Weiter?**

## Schritt 5: Session-Ende

Wenn Samuel /recap macht oder die Session beendet:

> **Focus-Fazit:**
> - Ziel: [Ziel]
> - Erreicht: Ja / Nein / Teilweise
> - Was geschafft: [Liste]
> - Geparkte Ideen: [Liste, falls vorhanden]

---

**Warum das hilft:** ADHS-Gehirne sind brillant im Starten, aber kaempfen mit Dranbleiben.
Focus Mode ist kein Kaefig — es ist ein Anker. Du kannst immer bewusst wechseln.
Aber unbewusst abdriften? Das faengt Focus Mode ab.

Du hilfst Samuel, eine Session sauber abzuschliessen. Kein Kontext geht verloren, keine Angst vorm Schliessen.

**Argumente:** $ARGUMENTS

---

## Was du tust:

### Schritt 1: Session-Scan

Geh die aktuelle Konversation durch und identifiziere:
- **Offene Faesser** — Themen die angesprochen aber nicht abgeschlossen wurden
- **Delegierte Tasks** — Dinge die an OpenCode, SubAgents, oder "spaeter" verschoben wurden
- **Unbeantwortete Fragen** — Fragen die im Raum stehen
- **Angefangene aber nicht getestete Aenderungen**
- **TODOs/Next Steps** die erwaehnt aber nicht umgesetzt wurden

Ausgabe als uebersichtliche Tabelle:

```
| # | Fass | Status | Aufwand |
|---|------|--------|---------|
| 1 | Kitty Theme testen | Offen — nicht verifiziert | ~2 min |
| 2 | SESSION_LOG updaten | Erledigt | — |
| 3 | Claude Code /theme | Offen — Hinweis gegeben | ~1 min |
```

Wenn wenig oder nichts offen ist, sag das ehrlich: "Sieht sauber aus, du kannst schliessen."

### Schritt 2: Modus waehlen

Wenn `$ARGUMENTS` den Wert "plan" enthaelt → springe direkt zu Schritt 3b (Plan-Modus), keine Rueckfrage.

Sonst: Samuel per AskUserQuestion fragen mit diesen Optionen:
- **Abarbeiten** — "Lass uns die offenen Punkte jetzt durchgehen und schliessen"
- **Plan sichern** — "Ich sichere alles als Planungsdatei, dann kannst du die Session schliessen"
- **Mix** — "Schnelle Sachen jetzt, Rest als Plan"

### Schritt 3a: Abarbeiten-Modus

- Offene Punkte nach Aufwand sortieren (kleinste zuerst → Quickwins)
- Jeden Punkt einzeln abarbeiten
- Nach jedem erledigten Punkt: kurzes Feedback und abhaken
- Am Ende: `/recap` vorschlagen

### Schritt 3b: Plan-Modus

Erstelle eine Datei `PLAN_[YYYY-MM-DD]_[THEMA].md` im aktuellen Projektverzeichnis (oder CWD wenn kein Projekt erkennbar).

Inhalt:

```markdown
# Plan: [Session-Thema]
Erstellt: [DATUM] aus Claude Code Session

## Kontext
[Was wurde in der Session gemacht, welche Entscheidungen getroffen]

## Offene Punkte
- [ ] Punkt 1 — [Details, Dateipfade, was genau zu tun ist]
- [ ] Punkt 2 — [...]

## Relevante Dateien
- `pfad/zu/datei` — [was dort geaendert wurde / werden muss]

## Entscheidungen die getroffen wurden
- [Entscheidung]: weil [Grund]

## Naechste Schritte (priorisiert)
1. [Erster konkreter Schritt]
2. [Zweiter Schritt]
```

Danach:
- Pfad zur Plan-Datei ausgeben
- Hinweis: "Du kannst diese Session jetzt sicher schliessen. Starte neue Session und sage: 'Lies PLAN_xxx.md und arbeite das ab.'"

### Schritt 3c: Mix-Modus

- Samuel per AskUserQuestion auswaehlen lassen welche Punkte jetzt abgearbeitet und welche als Plan gesichert werden
- Schnelle Punkte abarbeiten (kleinste zuerst)
- Rest in Plan-Datei sichern (wie 3b)
- Am Ende: `/recap` vorschlagen

---

## Regeln

- **Ehrlich sein** — Wenn wenig offen ist, sag das. Kein kuenstliches Aufblasen.
- **Aufwand realistisch schaetzen** — Kein "~2 min" fuer was 20 min dauert.
- **Plan-Dateien: genug Detail** — Eine NEUE Session muss damit weiterarbeiten koennen ohne Kontext zu verlieren. Dateipfade, konkrete Schritte, getroffene Entscheidungen.
- **Kein Schoenreden** — Wenn ein Task halb fertig ist, schreib "halb fertig", nicht "fast done".
- **Delegation beachten** — Fuer Abarbeiten-Modus die ueblichen Delegation-Regeln nutzen (/chef, /research etc.)

You are executing a **Cross-Model Review**. A different AI will review Claude's work to find blind spots.

**Arguments:** `$ARGUMENTS`

Parse arguments:

### Provider-Staerken (aus Eval mit echtem Code verifiziert)

| Provider | Denkstil | Beste fuer | Schwaeche |
|----------|----------|-----------|-----------|
| `minimax` | Pragmatischer Developer | Config-Luecken, unfertige Features, API-Design | Generischer, weniger unique Findings |
| `gemini` | Security Auditor | OWASP, Privacy, Output-Limits, Sandboxing | Uebertreibt manchmal (SRP, Overengineering) |
| `codex` | Reverse Engineer | Deep Code-Analyse, versteckte Bugs, Session-Logik | Kann halluzinieren bei Security-Vektoren |

## Process

### Step 1: Gather Context

Run these commands via Bash and capture ALL output:

```bash
# Git diff (what changed)
GIT_DIFF=$(git diff HEAD 2>/dev/null || echo "No git repo or no changes")

# If no diff against HEAD, try staged + unstaged
if [ "$GIT_DIFF" = "No git repo or no changes" ] || [ -z "$GIT_DIFF" ]; then
  GIT_DIFF=$(git diff 2>/dev/null || echo "No changes")
fi

# Recent commits
GIT_LOG=$(git log --oneline -10 2>/dev/null || echo "No git history")

# Project context
CONTEXT=$(bash ~/.claude/hooks/gather-context.sh "$(pwd)" "review" 2>/dev/null || echo "No context script")
```

Capture all three outputs: GIT_DIFF, GIT_LOG, CONTEXT.

### Step 2: Route to Provider

Build the following REVIEW_PROMPT (fill in the gathered context):

```

Fokus: {FOCUS_AREA}

{GIT_DIFF}

{GIT_LOG}

{CONTEXT}

2. **Sicherheitsprobleme** — OWASP Top 10 checken
3. **Architektur-Bedenken** — passt das ins Gesamtbild?
4. **Alternative Ansaetze** — gibt es einen besseren Weg?
5. **Gesamtbewertung** — ausfuehrlich und differenziert in Textform. Staerken UND Schwaechen benennen. Keine Ampel-Emojis oder vereinfachte Schemata — du bist ein vollwertiges Sprachmodell, nutze das.

```

get_pid_for_port() {
    local port="$1"

        local project service pid status

        pid=$(get_pid_for_port "$port")
        if [[ -n "$pid" ]]; then
            status="LIVE (pid $pid)"

            status="offline"
        fi

    printf "%s\n" "------|--------|------------------"

        local laddr port pid proc
        laddr=$(echo "$line" | awk '{print $4}')
        port="${laddr##*:}"
        pid=$(echo "$line" | sed -n 's/.*pid=\([0-9]*\).*/\1/p')
        proc=$(echo "$line" | sed -n 's/.*"\([^"]*\)".*/\1/p')
        if [[ "$port" =~ ^[0-9]+$ ]] && (( port >= 1024 )); then

        echo "REGISTRIERT (offline): $registered"
